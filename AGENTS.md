# AGENTS.md

DeepSeek Harness (DSH) plugin monorepo for **dsh-tool-web-enhanced-profile**: a code-free profile bundle that mounts two plugins and selects their `ctx.web` providers in the shared `web` row. The model keeps DSH's native `web_search`/`web_fetch` (tool-web); each plugin switches backends internally. Targets DSH `>=0.2.1-rc.2 <0.3.0-0`, Node `^22.19.0 || >=24.0.0`, pnpm 12. Design: [docs/architecture.md](docs/architecture.md) (Chinese). Workflow: [docs/development.md](docs/development.md). As-built code structure: [docs/code-structure.md](docs/code-structure.md) (Chinese).

## Layout

- `packages/profile` – `dsh-tool-web-enhanced-profile`: `cordis.patch.yml` (writes both `web` fields, disables `web-search-deepseek`, inserts the plugin rows and the menu row), locale, icon. No code.
- `packages/search-enhanced` – `dsh-web-search-enhanced`: row `web-search-enhanced`, provider `search-enhanced`. Keeps only what is specific to search: catalog, adapter wires and MCP result rows (`src/search/`), native backends, freshness, `settings/resolve.ts`, and the capability wiring in `src/host/` (`searchCapability`, connection status, freshness codec). Everything else comes from core; tests import core directly.
- `packages/fetch-enhanced` – `dsh-web-fetch-enhanced`: row `web-fetch-enhanced`, provider `fetch-enhanced`. Catalog `builtin:local` (default), `builtin:deepseek-fetch-api` and remote adapters Exa, Firecrawl, Tavily, Tinyfish; custom adapter connections. `src/local/` (allowlist rules, address policy, resolver around DSH's `HttpFetchProvider`), `src/backends/` (native), `src/remote/` (adapter wires, page→`WebFetchResult` mapping, transport constants, execution), `src/prompt.ts` (allowlist notice), `src/settings/`, `src/host/`, `src/client/` (local allowlist and User-Agent editors, service notes).
- `packages/ui` – `dsh-tool-web-enhanced-ui`: row `tool-web-enhanced-ui`; empty Host face, browser face with the `webConnections` service, the single composer connection menu, the activation prompt and the bundle overview (route status, upgrade preflight). Plugins register sections into it through optional injection and keep their own `/setup-*` commands and row settings pages. It must never depend on a plugin row: it works with either, both, or neither plugin row enabled.
- `packages/core` – private, source-only shared code, inlined into each plugin at build time. `./shared` (ids, connection grammar, settings document grammar, route, url, selection contract) must stay isomorphic (no Node, browser, or Host imports); `./host` holds the selection paradigm (`Capability`, `installCapability`, sessions, plans, restriction, Remote factory, route, credentials, bounded transport) and the remote backends' shared wire (MCP client, `AdapterWire` / `runAdapter` / `adapterTarget`); `./client` holds the section contract (sections and route facts), `useObservable`, `ConnectionSelectionStore`, route/pairings/credential status, the `/setup-*` command factory and the catalog-driven settings page skeleton (services, endpoint trust, custom connections).
- `build/` – one tsdown factory for every plugin, platform module table, decorator and CSS Modules plugins.
- `scripts/` – workspace discovery/packing, package verification, clean.
- `e2e/` – isolated real-DSH suite: `harness/` (environment, host boot, `dsh web`, Playwright), `fixtures/`, `*.e2e.ts`.

## Commands

- `pnpm install`
- `pnpm run check` – typecheck, type-aware oxlint, build, vitest, verify:package. Must pass before you finish.
- `pnpm run test:e2e` – run when touching the profile patch, provider registration, plugin-page metadata, browser faces, or the DSH baseline. Never touches the user's DSH home or running GUI. GUI specs need Chromium (`DSH_E2E_CHROMIUM`); `upgrade` installs the published 0.1.x predecessors from npm unless `DSH_E2E_PREDECESSOR_SEARCH` / `DSH_E2E_PREDECESSOR_FETCH` point at prebuilt checkouts. Screenshots land in `.e2e/artifacts`.

Test environment quirks (see docs/development.md): browser tests start with `// @vitest-environment jsdom`; `primitivesStub()` in `vitest.config.ts` stubs only the implementation libraries the published `dsh-client-ui-primitives` imports without shipping (`clsx` gets a real minimal implementation); `zustand` and `immer` are root devDependencies because the published `dsh-client-store` imports them at runtime without declaring them. Do not remove either without checking the DSH packages.

Do not run state-changing git commands unless asked. Do not add dependencies without approval. `ipaddr.js` is an approved devDependency of fetch (same version as DSH `web-fetch-http`), inlined into its Host bundle.

## Invariants

- Identities (package names, row ids, provider ids) are defined once in `packages/core/src/shared/ids.ts`; the profile test asserts the YAML patch matches them. Naming follows DSH: a row id is its npm name without the `dsh-` prefix (`dsh-tool-web-enhanced-ui` → `tool-web-enhanced-ui`), and the Cordis plugin name equals the row id. Provider plugins are the `web-*-enhanced` family; product-level packages (profile, ui, private core) are `tool-web-enhanced-*`.
- The profile writes **both** `web` fields together; nothing else in this repo writes the `web` row. Backend switching never touches it.
- Each plugin registers exactly one provider (its seat). New behaviour goes into the planner (which backend) or a backend (how), never a second registration.
- Plugins ship self-contained host bundles: runtime imports only Node built-ins and `@deepseek-ai/*`; no `dependencies`. `verify-packages` enforces it.
- search and fetch never import each other in `src`; shared code goes to core; core holds no module-level state. Composition tests may import another package's `src` to exercise the real seam (for example ui × search).
- `available()` does no I/O. Credentialed requests use `redirect: 'error'`. Keys live only in DSH Credentials (settings store `credentialRef`); an API key with characters other than printable ASCII and spaces is refused before any request. Keyless never reads, sends, or falls back to a key, and always uses the catalog endpoint (core `adapterTarget`). No automatic retry or fallback; switching to another backend after a failure is left to the Agent (the planned M5 `web_*_enhanced` tools).
- search and fetch share one selection paradigm: operator-defined connections in the row settings, a per-Session selection frozen per model request step, `null` = off (Seat error + `agent.ctx.tools.restrict`). Differences between the two are catalog data and capability parameters, never a second mechanism. Only "which connection" (plus session options) is frozen; whether it is still selectable (exists, enabled, not `model`) is judged per call by one rule (core `isSelectable`), and the execution target is rebuilt from current settings on every call. The restriction is installed only while the `web` row is confirmed to route to this plugin.
- Both rows use one settings document grammar (core `shared/settings.ts`: `version`, `defaultConnection`, `showSelector`, `defaults`, `connections`), validated by one pure function shared by Host and browser (each plugin's `resolveSettings` over core's `resolveDocument`). A custom endpoint, or a `url` option such as a native `baseURL` that differs from the catalog endpoint, needs `trustedEndpoint: true`. Unsafe keys (`__proto__`, `constructor`, `prototype`) are rejected; text and connection counts are bounded. 0.1.x settings are not read or migrated: the Host rejects them (the plugin still activates; calls fail with `WEB_PROVIDER_CONFIGURED_UNAVAILABLE`), the settings page names the fields and offers Reset. Future versions migrate through the pure N→N+1 table in `migrateDocument` (empty today).
- fetch: only the `local` connection (DSH's `HttpFetchProvider` plus our injected resolver) checks target addresses; an empty allowlist equals native public-only, and proxied hostnames are resolved by the proxy, as upstream does. Remote backends follow DSH's own design: the service owns target access policy; we reject redirects of the API request, keep cancellation, and state in the UI who receives the URL. Remote results are text; without a reported target status they are 200 for the requested URL (compatibility mapping), and only a status the service reports becomes a non-2xx result. `native` backends instantiate DSH's exported provider classes and keep their behaviour; only their error messages are restated. Our own egress uses global `fetch` only.
- Model-facing errors are `WebError` with an existing `WEB_*` code and a short actionable English message; never upstream bodies or secrets. Remote services (`<ns>/*`) pass contract errors through (invalid row settings are `<ns>/invalid-settings`) and turn anything else into `gateway/internal` with a fixed message; the original goes only to the Host log. UI text goes through locale dictionaries (zh and en, same keys) in each package's `src/client/locales.ts`; `locale/*.json` holds only the Plugins-page `meta`.

## Conventions

- Readable code over dense one-liners; small focused modules; JSDoc on exports only when it adds information.
- No over-defensive code: no error-swallowing try/catch, no shape-sniffing of private DSH internals, no `?.`/`??` piles for values that are always present, no timing-based correctness.
- Discriminated unions over bags of optional fields.
- Tests exercise behaviour at seams (real `WebRuntime`, real include patch algorithm, local HTTP servers, the real DSH in e2e). Mock only the network and the clock. Every bug fix gets a failing-first test.
- Keep docs in sync: behaviour changes update docs/architecture.md, the affected package README, and CHANGELOG.md.

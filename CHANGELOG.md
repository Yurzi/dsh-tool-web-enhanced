# Changelog

## v0.1.0 (2026-10-21)

### dsh-tool-web-enhanced-profile 0.1.0

- New bundle. Selects `search-enhanced` and `fetch-enhanced` in the shared `web` row (both fields), disables the native `web-search-deepseek` row, and mounts the two plugins and the menu row below.

### dsh-tool-web-enhanced-ui 0.1.0

- New package, mounted by the profile as row `tool-web-enhanced-ui`. The Host face is empty; the row exists so DSH loads the browser face. It works with either plugin row, both, or neither.
- The `webConnections` browser service: plugins register their menu sections and, separately, their route facts into it.
- One composer button for both capabilities. It shows each registered section's state in menu order ("Exa · Local HTTP", or Off, Couldn't load, Invalid settings, Connection removed), with a warning dot on a side that needs attention (load failure, invalid settings, a removed or unready connection, or routing to another provider). Its accessible name and tooltip read per side, for example "Search: Exa · Fetch: Local HTTP (needs attention)". When the composer's controls do not fit on one line, the button collapses together with DSH's model selector (it follows the row's `--dsh-composer-model-text-display` / `--dsh-composer-model-icon-display` instead of breakpoints of its own): the text hides and the dots move onto the globe icon, so the button never pushes the composer onto two lines.
- The menu has two layers: a panel for one capability above, and DSH's segmented tabs at the bottom, nearest the button, to switch between the capabilities (Search, then Fetch). It opens on the first with focus on its tab; ←/→ and Home/End move between the tabs, Escape closes it and returns focus to the button, and a tab carries the same warning dot as its side. All panels share one grid cell, so the menu keeps the tallest panel's height and does not jump when switching; only the list scrolls, and the selected row is scrolled into view. A panel's header shows the current connection and where the choice comes from ("This conversation", "Parent conversation", "Model's last choice", "Default connection"), with a settings button (gear icon) beside it; below are Off, the connections, the capability's own options, a loading state, a "Couldn't load" row that reloads when clicked, and a notice when the `web` row routes the capability elsewhere. When a capability's settings are invalid, its panel says "<capability> settings are invalid. Open settings to fix them." and points to that settings button, without a reload.
- Route facts come from the running plugins, including `DSH_WEB_SEARCH_PROVIDER` / `DSH_WEB_FETCH_PROVIDER`, even with `showSelector: false`. For a plugin row that is not running, the browser has no source for those variables and judges from the `web` row alone.
- With a plugin row disabled (search, fetch or both), its tab disappears and the menu and overview say the capability is unavailable; with no sections, the button is hidden.
- Activation prompt for the profile bundle. It runs the same upgrade preflight as the overview: when 0.1.x leftovers may keep web tools away from this bundle, it says so and points to the profile details. It never writes anything itself.
- Bundle overview on the Plugins page: whether each capability is routed to this profile, whether its plugin row is disabled, and an upgrade preflight for leftovers of 0.1.x (user-layer `web` overrides, coexistence-mode provider ids, a re-enabled `web-search-deepseek` row). "Remove leftover settings" appears only next to the leftovers it can fix and removes the user-layer `web` fields only after confirmation; nothing is rewritten silently.

### dsh-web-search-enhanced 0.2.0

- **Breaking:** no longer a bundle; install `dsh-tool-web-enhanced-profile`. Upgrading this package alone removes its row from the profile.
- **Breaking:** registers the provider `search-enhanced` instead of taking the native `deepseek-official` seat.
- **Breaking:** the settings format is redesigned and 0.1.x settings are not read. The document is `{ version: 2, defaultConnection, showSelector, defaults: { freshness }, connections }`, the same grammar as the fetch row. Retired top-level fields (`providerId`, top-level `freshness`, and the 0.0.x fields `modelMode`, `protocol`, `baseURL`, `model`, `fallbackModel`, `apiKey`, `apiKeyEnv`, `apiVersion`, `toolIdentifier`, `maxTokens`, `maxUses`, `chatSearchMode`, `searchContextSize`) are rejected with an error naming the field. The plugin still loads; searches fail with `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` until the settings are fixed. The settings page says "These search settings can't be read…" and offers Reset; a stored `apiKey` is hidden from the page and must be removed by hand.
- **Breaking:** `builtin:deepseek` and `kind: structured` are no longer accepted; use `builtin:deepseek-search-api` and `kind: adapter`. The 0.1.x model settings (`modelMode`, `protocol`, `chatSearchMode`, …) are not read; model search is configured anew as the connections below.
- Stored conversation choices and model memories from 0.1.x keep working; the storage format is unchanged.
- Session connections: each conversation chooses a connection or Off; the choice is frozen per model request step, forks inherit it, and whether the connection is still enabled, along with its endpoint, key reference and options, is read on every call.
- Model memory is visible and clearable: choosing a connection remembers it for the conversation's model, the composer shows when a choice came from memory, and the settings page lists every memory with a clear button.
- Nine built-in connections: native `deepseek-messages` (default, same as native DeepSeek search) and `deepseek-search-api`; the model connection `session-model` (below); adapters Exa, Firecrawl, Tavily, Tinyfish, OpenAlex and Semantic Scholar (keyless where the service allows it; Exa and Tinyfish keyless go through their hosted MCP tools). Operators can add custom adapter connections and custom model connections.
- Off hides `web_search` from that conversation's Agent from the next request step, while the `web` row routes search to this plugin; calls that still arrive get an error. When the `web` row changes, conversations already seen by the plugin are rechecked at once.
- Row settings page on the Plugins page, driven by the catalog and shared with fetch: default connection, built-in services (enable, access, credential name, write-only key, options), custom connections, model memory, route notice, Reset. Writes are sparse and validated before they are saved. Each built-in connection can use another DSH Credentials name (empty means the catalog's name). A native `baseURL` can be overridden like on the native row, but only together with `trustedEndpoint: true`; on the page an "I trust this address" switch confirms it. Trust belongs to the address it was given for: changing the address asks again, and turning the switch off revokes the trust and returns to the official endpoint in one write. The same applies to custom connections. Switching a service back to keyless also removes, in the same write, options the keyless route does not accept. Yes/no options offer Default, On and Off. Removing a custom connection resets `defaultConnection` only when it named that connection. Custom connection rows say which service receives the query.
- In the composer menu, ready connections show their access and, for remote services, who receives the query ("No key needed · the query is sent to Exa"); unavailable ones give a short reason ("Needs an API key", "Needs a DeepSeek account or API key"). Freshness uses DSH's segmented control.
- `/setup-search` command to choose or turn off the conversation's connection and set freshness; it works with or without the composer menu (`showSelector: false` hides only the menu section).
- Model-facing errors are short and actionable, for example "<connection> could not complete the search…" for a failed hosted MCP tool. An API key containing a line break or another control character is refused before any request with `WEB_PROVIDER_CREDENTIAL_MISSING`, naming only the credential.
- Model search: a third backend kind, `model`, asks a model with a server-side web search tool to run the search. One non-streaming request through the same bounded transport (redirects refused, 2 MiB, 90 s, no retry); the model's answer is returned as `content` exactly as written (adjacent text blocks joined, a blank line where a tool block sits between them, never trimmed or cut), and the sources it cites go through the same source filter as every other connection. Answers without a search or with a tool error block are returned as they are, for the Agent to judge. Protocols: Anthropic Messages, OpenAI Responses and OpenAI Chat Completions.
- `builtin:session-model` ("Conversation model"): follows the model of the request that made the call, read again on every call (never frozen in the step plan). DeepSeek's two official routes are handled in one place: the session's endpoint (configured `baseURL`, then `DEEPSEEK_BASE_URL`, then `https://api.deepseek.com/anthropic`) and the session's credential (`apiKeyEnv`, default `DEEPSEEK_API_KEY`; the account route uses the account sign-in and never falls back to an API key). Other routes are followed when DSH's Models settings declare one of the three protocols (`api`), with no custom headers and an endpoint not built from an environment variable. When the route cannot be followed, the menu says why (no model yet, unreadable provider settings, no supported protocol, no fixed endpoint, custom headers, no single API key) and calls fail with `WEB_PROVIDER_CONFIGURED_UNAVAILABLE`; the plugin never switches connection on its own. Enabled by default; it is used only when a conversation chooses it. Overrides accept only `label`, `disabled` and `options`.
- Custom fixed model connections: `custom:<name>` with `kind: model`, `protocol`, `model`, a required `endpoint`, `trustedEndpoint: true` (always required) and `credentialRef` (DSH Credentials only).
- Defaults follow each vendor's current standard, and other vendors' compatibility is tuned through options: Anthropic `web_search_20260318` with `max_uses` 5 and `max_tokens` 4096; Responses `web_search` with `tool_choice: auto`, sources included and `store: false`; Chat Completions `web_search_options`. Options per protocol: `maxTokens`, `anthropicTool`, `maxUses`, `allowedCallers`, `responseInclusion`, `responsesTool`, `searchContextSize`, `externalWebAccess`, `returnTokenBudget`, `allowedDomains` / `blockedDomains` (Anthropic allows only one of the two), and the approximate user location. A custom connection takes its protocol's options; the conversation model takes all of them and applies those of the route it follows.
- DeepSeek dialect: when following a DeepSeek route, the Anthropic tool defaults to `web_search_20250305` and thinking is disabled, as in DSH's own DeepSeek search (an explicitly set tool version wins). Tested against DeepSeek's API on 2026-10-21: Messages accepts only the two dated tool versions and returns sources without quotes; Responses searches only on `deepseek-v4-pro` and returns no sources; Chat Completions has no server-side search.
- Settings page: the conversation model row has its options grouped by the protocols that apply them, and says that the query goes to the model's provider and that server-side search is billed per search. Custom connections offer "Model search · <protocol>" formats with a model id, a required endpoint and endpoint trust. Domain lists are edited one entry per line; where only one of the two lists is allowed, setting both is flagged on both fields and nothing is saved. Clearing a conflict saves the cleared option and the held valid draft atomically against one settings revision. In the composer menu, model connections say who receives the query, and an unavailable conversation model gives its localized reason.
- Model search reads other plugins' route settings only within bounds (lengths and counts are checked before anything is parsed; anything over budget is reported as unsupported, without echoing the value), and checks a DeepSeek account token for printable ASCII before sending it; a malformed token is neither sent nor logged.
- The 0.1 fallback to "the only usable connection" is gone.
- Errors carry the upstream's own explanation after this plugin's short message, so the Agent can judge the failure: `<connection> responded (untrusted): …` for HTTP errors (also for model connections) and hosted MCP tool or server errors, `The search service responded (untrusted): …` for an API error envelope. The native connections add `DeepSeek responded (untrusted): …` with DeepSeek's report only (DSH's settings advice for its own built-in row is left out), after a short message that no longer blames the key first ("DeepSeek search failed. If every query fails, ask the user to check …"). Explanations are at most 2000 characters and marked untrusted; without one the message is unchanged. The request's API key or account token is kept out of what the model sees (except fragments shorter than 8 characters inside DSH's own native parse errors): an error body, MCP error or DeepSeek report that contains it (whole or an 8-character fragment) is withheld as a whole ("<connection>'s response was withheld because it contained this request's credential."), and in successful responses (API error envelopes inside them, model answers) it is replaced by `[redacted]`. Every Host log entry is a redacted copy.

### dsh-web-fetch-enhanced 0.2.0

- **Breaking:** no longer a bundle; install `dsh-tool-web-enhanced-profile`. Upgrading this package alone removes its row from the profile.
- **Breaking:** registers the provider `fetch-enhanced` instead of taking the native `http` seat.
- **Breaking:** the settings format is redesigned and 0.1.x settings are not read or migrated. The allowlist, User-Agent and limits are now options of the `builtin:local` connection. Retired top-level fields (`schemaVersion`, `providerId`, `allowCidrs`, `allowHostnames`, `userAgent`, `maxResponseBytes`, `maxBodyChars`, `timeoutMs`, `maxRedirects`) are rejected with an error naming the field. The plugin still loads; fetches fail with `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` until the settings are fixed. The settings page says the settings can't be read and offers Reset; after Reset, re-enter the allowlist on the settings page.
- Switchable fetch connections, the same way search works: each conversation chooses a connection or Off from the composer menu or `/setup-fetch`; the choice is frozen per model request step, forks inherit it, model memory is visible and clearable, and Off hides `web_fetch` from that conversation's Agent while the `web` row routes fetch to this plugin.
- Built-in connections: `builtin:local` (default; DSH's own HTTP(S) transport, same as native public-only fetch), `builtin:deepseek-fetch-api` (DSH's DeepSeek Fetch API provider; API key `DEEPSEEK_API_KEY` or DeepSeek account; a `baseURL` override needs `trustedEndpoint: true`; error messages restated), and the remote services below.
- `builtin:local` options: `allowCidrs` and `allowHostnames` (operator allowlist for non-public addresses; empty means public-only), `userAgent` (an empty value sends an empty header), `maxResponseBytes`, `maxBodyChars`, `timeoutMs`, `maxRedirects`. Defaults equal the native `web-fetch-http` row. Direct requests check the whole DNS answer set and NAT64 and pin the connection; IP literals are checked before the transport sees them. Errors from DSH's transport reach the model unchanged; local-generated errors (allowlist, DNS, cancellation, unexpected failures and rule validation) carry the `dsh-web-fetch-enhanced: ` prefix. Hostnames reached through a proxy are resolved by the proxy, and the rules cannot limit them.
- When this step uses `builtin:local` with a non-empty allowlist and the `web` row routes fetch to this plugin, the model is told which ranges the operator allowed.
- Remote connections: `builtin:exa`, `builtin:firecrawl`, `builtin:tavily` (keyless by default, or a personal key `EXA_API_KEY` / `FIRECRAWL_API_KEY` / `TAVILY_API_KEY`) and `builtin:tinyfish` (personal key `TINYFISH_API_KEY` only; an anonymous fetch route is not documented). Exa keyless goes through Exa's hosted MCP tool `web_fetch_exa`; the others call the service's REST API. The URL is sent to the service exactly as requested, and the service decides what it can reach; this plugin does not check the target address. The settings page and the composer menu say which service receives the URL, and the settings page notes how each service caches or keeps what it receives.
- Remote results are text. A service that does not report the target's status gives `statusCode: 200` for the requested URL (the service retrieved the page, as with DSH's DeepSeek Fetch API provider); Firecrawl's reported status and final URL and Tinyfish's final URL are used. A per-URL failure that comes with the target's HTTP status (for example a 404) is a result with that status and an empty body; other failures map to `WEB_FETCH_TIMEOUT`, `WEB_FETCH_TOO_LARGE`, `WEB_INVALID_URL` or `WEB_PROVIDER_ERROR` with short messages that name the connection. Bodies are capped at 100 000 characters and marked truncated; for Exa, a body that fills the requested character budget is marked truncated too. Remote calls refuse API redirects, read at most 5 MB and have a 120 s overall deadline. An API key containing a line break or another control character is refused before any request.
- Custom fetch connections: `custom:<name>` with `kind: adapter` and one of `exa`, `firecrawl`, `tavily`, `tinyfish`; always a personal key; a non-official `endpoint` needs `trustedEndpoint: true`. `defaultConnection` may name one.
- Row settings page on the Plugins page, driven by the catalog with the same rules as search (credential names, endpoint trust, keyless options, Default/On/Off for yes/no options, default reset on removal): default connection, connections, custom connections, model memory, route notice, Reset. The local allowlist editor checks each line (syntax, suggested fixes, duplicates, warnings for broad, loopback, metadata and public ranges) and saves both lists together only when you press Save. Other fields save sparsely when you finish editing.
- The composer menu shows "<access> · the URL is sent to <service>" for ready remote connections, and a connection that needs a key says so ("Needs an API key"; native connections "Needs a DeepSeek account or API key").
- The Plugins-page description names the remote reading services.
- Errors carry the service's own explanation after this plugin's short message, so the Agent can judge the failure (for example DeepSeek's `HTTP 404 failed to fetch URL` for a page it cannot reach): `<connection> responded (untrusted): …` for HTTP error bodies, per-URL failures reported in a successful response, and MCP tool or server errors; `DeepSeek responded (untrusted): …` for `builtin:deepseek-fetch-api`, with DeepSeek's report only and a short message that no longer blames the key first ("DeepSeek fetch failed. If every URL fails, ask the user to check …"). Explanations are at most 2000 characters and marked untrusted; without one the message is unchanged. The request's API key or account token is kept out of what the model sees (except fragments shorter than 8 characters inside DSH's own native parse errors): an error body, MCP error or DeepSeek report that contains it (whole or an 8-character fragment) is withheld as a whole ("<connection>'s response was withheld because it contained this request's credential."), and in successful responses (per-URL failure text inside them, page bodies) it is replaced by `[redacted]`. Every Host log entry is a redacted copy.

### dsh-tool-web-enhanced-core (private, not published)

- `./shared`: identities (`ids`), connection grammar and option rules (`validateOptions`; `keyless: false` or a narrowed enum limits an option on the keyless route), the route check both faces use (`routeOf`), URL checks, the per-Session selection vocabulary and the `selectionContract` Remote factory (`<ns>/get`, `set`, `provider`, `pairings`, `forgetPairing`), and the settings document grammar both rows use (`resolveDocument`; custom connections use the catalog's adapter entries, persisted as `CustomConnection`), version detection (`documentVersion`; an omitted `version` always reads as 2, and from version 3 on hand-written documents must state it) and the future migration pipeline (`migrateDocument`, empty today).
- `./host`: the selection paradigm both plugins install with `installCapability(ctx, capability)`: per-Session selections (queueing, revisions, fork inheritance, model memory, resolution order and source), per-step plans that freeze only the connection id and session options, route-guarded tool restriction, the Remote service factory, route detection, credential resolution and the bounded HTTP transport.
- `./host` also holds the remote backends' shared wire: the MCP client (`createMcpClient`; SSE is scanned line by line in linear time and accepts mixed line endings) and `AdapterWire` / `runAdapter` / `adapterTarget`, so the keyless rules (never read or send a key, always use the catalog endpoint) and the API key check (printable ASCII and spaces only, refused before any request) live in one place for both plugins.
- The Remote service factory sanitizes failures: contract errors pass through unchanged; invalid row settings (`InvalidSettingsError`, a `WebError` thrown by `settingsRow`) become the contract error `<ns>/invalid-settings` with a fixed message; anything else becomes `gateway/internal` with a fixed message, and the original error goes only to the Host log. The browser store reports `readFailure: 'invalid-settings' | 'failed'`.
- For search's model backend: `isSelectable` no longer excludes `model` connections (exists and enabled is the whole rule); connection views carry a closed `reason` for `unsupported` (`UNSUPPORTED_REASONS`) instead of an English `detail`; the settings grammar has a `model` branch for custom connections (`customConnectionSchema(adapterKeys, protocolKeys)`, `CustomConnection<A, P>`, `ProtocolDescriptor`, `resolveDocument({ protocols })`; catalog and protocol entries may declare `exclusive` option pairs, checked by `validateOptions` and on the settings page; catalog entries of kind `model` resolve to the Session route); `storedApiKey` (shared by `runAdapter` and the model backend), `routeApiKey` and `routeKeyConfigured` (DSH's model-route credential rule) join the Host credentials; the settings page skeleton gains list fields, protocol-grouped options (`protocolGroups`) and the custom model connection form. fetch passes no protocols, so it still rejects `kind: model`, now on the `kind` field.
- No behaviour change: the remote services' protocols moved from the plugins into core, one module per service (`providers/<service>.ts`) with one named wire per capability (`exaSearch` / `exaFetch`, `firecrawlSearch` / `firecrawlFetch`, `tavilySearch` / `tavilyFetch`, `tinyfishSearch` / `tinyfishFetch`, `openalexSearch`, `semanticscholarSearch`) instead of a provider table, so each plugin's Host bundle carries only its own side's parsing. The capability vocabularies moved with them (`SearchInput`, `SearchRow`, `SearchOutcome` with a closed `SearchInvalidReason`; `FetchInput`, `Page`, `PageOutcome`), and `FRESHNESS` moved to `./shared`. Wires never word model-facing errors: search maps every outcome through `mapWire(wire, searchSources)` and keeps its messages word for word; fetch binds the core wires directly and keeps `fetchResult` / `pageFailure`. Adapter tests keep their behaviour assertions;
- Upstream explanations in model-facing errors, shared by both plugins: the bounded transport reads at most 16 384 bytes of an HTTP error body and appends the service's explanation (`error`, `error.message`, `message`, `detail`, else the text) after the status message; the MCP client passes tool and JSON-RPC error text to the capability's `toolFailed` / `serverError(label, detail)` (`upstreamDetail` / `upstreamSuffix` word the appended part); search API envelopes and fetch page failures carry the service's text as `detail`; `restateNative` keeps the first paragraph of DSH's error after the capability's short message. `upstreamText` bounds an explanation to 2000 characters. The new `redaction` module (`secretMatcher`, `containsSecret`, `redactJson`, `redactDiagnostic`) handles this request's API key or account token in two contexts: error text that contains it (whole or an 8-character fragment) is withheld as a whole, and successful bodies get `[redacted]`; every `onDiagnostic` entry (transport, MCP, native, model, and both execution layers) receives a redacted copy without cause or stack, failed credential resolvers log a fixed local message, and a body that is not JSON logs a fixed parse diagnostic that quotes nothing from the body. Callers hand the credential to the transport as `Upstream.matcher`; `runAdapter` also redacts the parsed result, covering text reconstructed from JSON property names such as OpenAlex inverted abstracts; `native` records the credentials it hands to DSH per call through `nativeAuth`.
- `./client`: the browser section contract (`ConnectionSection`, `SelectionStore`, `RouteStore`, `WebConnectionsService` with `registerRoute` and `routes`) with `useObservable`, and the shared browser parts: `ConnectionSelectionStore`, `RouteStatus`, `PairingsStatus`, `CredentialStatus`, sparse writes, the `/setup-*` command factory, the settings document view (`effectiveDocument`, validation and revision-fenced writeback) and the catalog-driven settings page skeleton: the services list renders every catalog entry (access, credential name, URL options with endpoint trust, option form with optional hints); plugins add per-entry notes and access summaries and register extra editors by catalog key; the custom connection section and editor are shared.
